# Permissions and data storage

## Manifest permissions

| Permission     | Purpose                                                                                 |
| -------------- | --------------------------------------------------------------------------------------- |
| `activeTab`    | Temporary page access after the user invokes the extension.                             |
| `contextMenus` | Send the current selection to the Side Panel.                                           |
| `scripting`    | Run fixed bounded operation functions in the current page.                              |
| `sidePanel`    | Host the agent and user interface.                                                      |
| `storage`      | Store settings, credentials, installed skills, and undelivered context-menu selections. |
| `tabs`         | Identify the active tab and its URL when the user switches tabs or windows.             |

## Optional host permissions

| Permission   | Purpose                                                                                                                                            |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `<all_urls>` | Satisfy Chrome's `captureVisibleTab()` requirement after temporary `activeTab` access ends. Requested only from the first screenshot confirmation. |

Chrome describes `<all_urls>` as access to all sites. Pi Browser Agent declares it as optional rather than required, requests it only from the screenshot confirmation's Confirm gesture, and rechecks it before every capture. The runtime continues to target only the active visible HTTP(S) tab in the focused window, reject stale tab contexts, capture only the viewport, and cap the PNG at 3 MB. Denial leaves the confirmation open; revocation causes the next screenshot request to ask again. Screenshot content is sent to the selected model provider and stored in the session transcript. Opening the local annotation editor or attaching its rendered PNG requests no additional Chrome permission; only sending that new composer image shares it with the provider.

## Optional API permissions

| Permission  | Purpose                                                                                             |
| ----------- | --------------------------------------------------------------------------------------------------- |
| `bookmarks` | Search bookmark titles and URLs or read a bounded recent-bookmark list after explicit confirmation. |

`bookmarks` is absent by default. A bookmark tool request first opens Pi Browser Agent's operation confirmation unless the same operation, query, and limit were previously approved under Balanced or Convenient. If access has not been granted, its Confirm button requests the optional permission from the user gesture; denial leaves the operation unapproved. The service worker checks the grant again before every read. Chrome grants the bookmarks API as one capability that can also support writes, but Pi Browser Agent has no create, update, move, remove, tree-read, import, or export runtime method. The production artifact audit rejects bookmark mutation calls.

Optional host patterns cover `<all_urls>`, the two OpenAI authentication origins, and HTTP(S) page/provider origins. `<all_urls>` is requested only for screenshot capture. Chrome treats that broad grant as satisfying narrower origin requests, so a later exact-origin request can succeed without another native Chrome prompt. Pi Browser Agent therefore also records each normalized exact origin approved through an explicit Send, login, site-access, catalog-load, or cross-origin confirmation action. Approval updates serialize through a profile-wide Web Lock so concurrent trusted extension pages cannot lose additions. Ordinary access requires both Chrome host permission and this app-level approval; `<all_urls>` alone does not authorize a new page or provider origin. Independently granted exact Chrome origins are migrated into this approval list when detected.

OpenAI authentication origins are requested together only after the user chooses **Sign in with an account** and **OpenAI Codex (legacy)**; choosing an authentication method or entering a static API key requests no provider endpoint access. When the user submits a prompt, the Side Panel approves the visible page origin and the exact selected model endpoint origin in one user gesture before starting or queueing the task. Radius approves `radius.pi.dev` while loading its dynamic catalog. The account menu keeps **Allow current site** as a manual retry. Confirming cross-origin navigation or a cross-origin link approves the destination origin as part of that confirmation. Selecting the extension action also grants temporary `activeTab` access to the page visible at that time. There is no production `host_permissions` grant and no host access or app approval occurs without a user gesture, except migration of an independently granted exact Chrome origin.

The extension CSP permits HTTP(S) connections so a user-selected built-in provider can operate after Chrome grants its optional host permission. It still permits scripts only from the packaged extension and does not permit remote scripts. Screenshot and bookmark access can be revoked separately from Chrome's extension settings. A later protected operation fails or returns to its explicit confirmation flow without an automatic background permission request.

`browser_scroll`, `browser_select_option`, and `browser_get_element_details` add no Chrome permission or persistent store. They require the current site's existing Chrome permission and app approval. Scroll and details need no operation confirmation; native option selection always requires fresh confirmation. Scroll/selection discard volatile element snapshots. Returned viewport or element metadata follows normal model-tool and transcript storage. Details expose no field values. See [browser interaction tools](browser-interactions.md).

## Remote MCP permissions and storage

MCP uses the existing optional HTTPS host pattern; it adds no required permission. **Test and enable** is the only MCP host-request gesture. Authorization also requires a stored connection approval for the full normalized endpoint and its configuration revision. A screenshot grant alone cannot approve a server. Chrome's hostname patterns do not include a port or path; MCP checks both independently on every request.

The Side Panel owns MCP clients. It checks trusted configuration, endpoint approval, token binding, and Chrome permission before each request. Settings edits, disablement/removal, panel shutdown, and host permission revocation cancel local MCP work. No server connection or interrupted call is restored from a transcript.

Two versioned `chrome.storage.local` keys are restricted to trusted contexts and updated together under a cross-context Web Lock:
- `piBrowserAgentMcpServersV1`: at most eight public server records, including IDs, revisions, exact endpoints, enablement, connection approvals, and whether authentication is configured.
- `piBrowserAgentMcpTokensV1`: optional bearer tokens bound to a server ID, revision, and endpoint.

Remove servers individually to delete these settings and tokens. **Clear all session data** deletes conversation records, not MCP configuration. Existing transcripts can retain tool declarations, arguments, and results until the sessions are deleted or compacted. Older builds ignore the new keys; remove servers before downgrading if the tokens must not remain. See [remote MCP](mcp.md).

## Skill permissions and storage

The Skills picker reads only the UTF-8 `SKILL.md` selected by the user. It adds no manifest or host permission and grants no general filesystem access, directory traversal, or local-file page-tool access. Import, review, and enablement make no model request. A later submitted run shares enabled metadata; `skills_load({id})` can return a reviewed body from that run's enabled snapshot. Changes apply to the next run.

Skills use the trusted `chrome.storage.local` key `piBrowserAgentSkillsV1`, separate from settings, credentials, MCP records, and sessions. The exact envelope is `{version:1,records:[...]}`. Each record contains only `{id,name,description,body,enabled}`. Imports start disabled; explicit replacements retain the ID and start disabled. Cross-context writes serialize through a Web Lock and publish the complete envelope in one write. Failed writes leave the previous valid data unchanged; invalid stored records fail without being overwritten.

Limits are 65,536 UTF-8 input bytes, 64 UTF-16 name units, 512 UTF-16 description units, 20 installed records, 524,288 UTF-8 serialized store bytes, 16,384 UTF-8 serialized enabled-catalog bytes, and 131,072 UTF-8 loaded-result bytes per run, including JSON wrapper overhead and repeated loads. See [the exact format and budget definitions](skills.md).

Disable or delete skills in Settings to block loads in later runs. This does not erase loaded bodies from saved transcripts; delete affected sessions separately. **Clear all session data** does not remove skills. For corrupt-store recovery or downgrade cleanup, remove only `piBrowserAgentSkillsV1` from trusted extension storage as described in [skill recovery](skills.md#storage-and-recovery); do not clear credentials or unrelated settings. Older builds ignore this separate key.

## Microphone access

Microphone access is a Chrome content permission for the extension origin, not a manifest permission. Chrome suppresses microphone prompts in Side Panels, so selecting the microphone without an existing grant opens a full packaged Pi Browser Agent access tab. Only its explicit **Allow microphone access** button calls `getUserMedia({ audio: true })`; the temporary stream is stopped immediately after Chrome records the grant. The Side Panel then uses Chrome's Web Speech API for dictation. Spoken audio may be processed by Chrome's speech service, while only the editable transcript is sent to the selected model provider after the user selects **Send**. Users can revoke the grant from Chrome microphone settings; Pi Browser Agent stores no separate microphone approval.

## Storage

| Store                                 | Data                                                                                                                                                                                                                                                                                           | Lifetime                                                                                                                                |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `chrome.storage.local`                | Installed skill records (including disabled bodies), provider-scoped API keys or Codex OAuth credential, selected provider/model/thinking level, confirmation mode, interface preferences, instructions, active session ID, app-approved exact host patterns, Convenient approval fingerprints | Until removed, mode changed, or extension data cleared (Convenient fingerprints); settings and other records retain their own lifetimes |
| `chrome.storage.session`              | An undelivered context-menu selection and Balanced approval fingerprints                                                                                                                                                                                                                       | Browser session (or until manually cleared/mode changed for approval fingerprints)                                                      |
| IndexedDB `pi-browser-agent-sessions` | Versioned complete messages and tool results, including loaded skill bodies, confirmed bookmark titles and URLs, sent selected-element JSON, model state, names, timestamps, embedded original screenshots and sent pasted/annotated image content                                             | Until retention deletion or user clear                                                                                                  |
| Memory                                | Live agent, partial stream, confirmations, login cancellation, picker token/overlay state, unsent selected-element chips, unsent pasted/annotated image previews, and editable annotation strokes                                                                                              | Side Panel, page, or worker lifetime as applicable                                                                                      |

Local extension storage is restricted to trusted contexts. Content injection has no storage API channel and receives only operation parameters. Strict confirms each protected operation; Balanced (new-install default) remembers the same operation and target until Chrome restarts; Convenient remembers them across restarts. Existing installations without a saved mode remain Strict. Approval fingerprints are SHA-256 digests of bounded, canonical action identities, capped at 256 per mode; raw WebMCP arguments, bookmark queries, and full URLs are not kept in the approval ledger. Settings can clear both ledgers; switching modes clears them automatically. Form submissions, downloads, and clicks lacking a stable target always prompt. Chrome-owned permission requests are never cached or suppressed by these modes.

## Retention and recovery

Confirmed bookmark results are sent to the selected model provider as conversation tool results and then persist in the same transcript record as other complete messages. Search requires a non-empty query; search and recent reads return at most 50 normalized items and 50 KB. Pi Browser Agent does not keep a separate bookmark cache or index.

Clipboard images are read only after an explicit paste into the composer. Screenshot annotation reads an already completed screenshot tool result locally and produces a new PNG only after the user draws and chooses **Attach**. One message accepts up to four PNG, JPEG, WebP, or GIF images with a combined binary size of 3 MB. Images remain in memory until sent or removed; sent images are embedded in the transcript. The original screenshot and an annotated copy are separate images and can both count toward the 5 MB session limit.

The element picker runs only after its composer button is selected and exact current-site access is approved. Up to five contexts using at most 16 KB combined remain memory-only until sent or removed and are cleared on tab-context or session changes. Each context can include the page URL, tag, bounded ID/classes/visible text/accessibility metadata, allowlisted attributes, viewport rectangle/scroll metadata, and a best-effort selector. It excludes input values, hidden text, full HTML, URL credentials, iframe contents, and Shadow DOM. After Send, the versioned context is embedded as explicitly untrusted JSON in the user message, sent to the selected model provider, and retained with that message.

IndexedDB retains up to 50 sessions, newest first, except records protected by live ownership or invalid tree data awaiting explicit removal. Each serialized session is limited to 5 MB. Legacy linear transcripts can remove embedded images and then the oldest messages to fit, and the Side Panel reports the loss. Tree-enabled sessions never use this destructive compaction: all branches, images, metadata, and the duplicated active transcript projection count toward the same 5 MB limit, with at most 5,000 nodes. Oversized writes fail and report the unsaved state; the previously stored record remains intact. Session writes and retention deletes use one transaction. The active session ID is stored separately so Side Panel and Chrome restarts restore the selected session even when records have equal timestamps. Deleting a session deletes its transcript and inline image content in the same record. Clearing session storage removes the object store contents before creating a new empty session.

`/tree` adds an optional versioned tree to the existing schema-version-1 record without changing the IndexedDB database version. Preview and cancel do not rewrite legacy sessions. The first successful navigation writes a validated tree and active transcript atomically. Node IDs and parent links preserve abandoned paths; only the active path is sent on a later explicit request. Selecting a historical user message restores its text and validated raster images to the composer, not stale element-picker chips. Malformed trees or active-projection mismatches fail closed without deleting or treating the record as legacy. Deleting or clearing a session removes every branch and embedded image in that record.

Before downgrading, preserve a copy of complete IndexedDB session records. Older extension builds can read the active `messages` projection but ignore tree metadata and can discard inactive branches on later saves. Do not use an older build to write tree-enabled sessions when those branches must be retained.

A session is `running` only while an agent invocation is active. A Web Lock prevents two live Side Panels from owning the same session. Startup changes only a successfully claimed stale `running` record to `interrupted`. Partial streaming state is memory-only; completed messages remain available for review, and mutation tools are not replayed.
