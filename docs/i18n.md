# Interface languages

Pi Browser Agent supports 18 interface languages. English is the default and fallback. All extension layouts remain left-to-right (LTR).

| Language             | Application locale | Chrome catalog |
| -------------------- | ------------------ | -------------- |
| English              | `en`               | `en`           |
| Traditional Chinese  | `zh-TW`            | `zh_TW`        |
| Japanese             | `ja`               | `ja`           |
| Korean               | `ko`               | `ko`           |
| Spanish              | `es`               | `es`           |
| French               | `fr`               | `fr`           |
| German               | `de`               | `de`           |
| Portuguese           | `pt`               | `pt_PT`        |
| Brazilian Portuguese | `pt-BR`            | `pt_BR`        |
| Italian              | `it`               | `it`           |
| Dutch                | `nl`               | `nl`           |
| Polish               | `pl`               | `pl`           |
| Turkish              | `tr`               | `tr`           |
| Russian              | `ru`               | `ru`           |
| Indonesian           | `id`               | `id`           |
| Vietnamese           | `vi`               | `vi`           |
| Thai                 | `th`               | `th`           |
| Hindi                | `hi`               | `hi`           |

Simplified Chinese and RTL layouts are not supported. User messages, page text, and model answers can still contain other languages.

## Select a language

1. Open **Settings → Appearance → Language**.
2. Select a language or **Follow browser**. Each explicit choice shows its native name and locale code.
3. Select **Save general settings**. The Settings tab closes. Other open views apply the saved language when their current operation finishes.

Language has no preview. Cancel, Back, and Escape use the normal draft protection. A cancelled or failed save does not change the active language. Another open Settings tab keeps its own drafts and display language. An unrelated save retains a language change made in another tab if the local language selection was not edited. The latest language is read inside the serialized settings commit, including when approval clearing delayed the save.

A language change does not reload the conversation, send a model request, change instructions, or rewrite a session. An active run, dialog, picker, dictation operation, or open command/menu finishes before the interface changes. Existing message content, attachments, disclosure state, and clipboard work remain intact.

Select **English (`en`)** to restore the default interface. This does not clear any stored data.

## Follow browser

Explicit language choices do not depend on the browser language. **Follow browser** checks `navigator.languages` in order. It uses `navigator.language` if that list is empty.
- Match a supported canonical BCP 47 tag, then a supported base language. Ignore invalid tags.
- Resolve Portuguese with a Brazilian region to `pt-BR`. Resolve other Portuguese variants, including `pt-PT`, to `pt`.
- Resolve `zh-Hant` and its variants to `zh-TW`. An explicit script has priority over the region.
  - Without a script, `zh-TW`, `zh-HK`, and `zh-MO` resolve to `zh-TW`.
  - An explicit `zh-Hans` script, `zh-CN`, `zh-SG`, and ambiguous `zh` do not select Traditional Chinese.
- Continue to the next browser preference when a tag is unsupported. Use English if none match.

Chrome's manifest description, action title, and shortcut description follow Chrome's own language. The manual application selection does not override these native labels. The extension's selection context menu follows the saved application selection and is refreshed when the worker starts or the selection changes.

Dictation still uses the browser language. Interface selection does not set the language of model answers. Provider-owned credential prompts and arbitrary browser, provider, and runtime diagnostics can remain in their original language. Diagnostic redaction still applies.

## Catalog ownership

`src/browser/i18n/en.ts` defines English source messages, message-key types, and plural messages. `src/browser/i18n/<locale>.ts` contains each translated catalog. `catalogs.ts` registers the bundled catalogs; `locales.ts` defines the allowed preferences and matching rules. `index.ts` provides typed lookup and named-parameter interpolation. No catalog is fetched from the network.

English source messages are the catalog keys. Use fixed trusted keys at the call site, not page content, model output, skill data, provider errors, or remote metadata. Changing an English key requires changing every catalog and its callers.

Use complete messages and named parameters. Preserve each parameter in every translated form. Count-bearing plural messages must supply every cardinal category that `Intl.PluralRules` reports for that locale. A missing message falls back directly to English, never through another Portuguese variant. Tests require complete catalogs before release.

`dom.ts` captures text nodes and presentation attributes from the packaged HTML before controllers insert data. It retains only those original bindings. It does not scan or observe later model, page, skill, or MCP content for translation. Code and editable content are excluded. Attribute updates include accessible names, tooltips, alternatives, and restored search placeholders. Catalog text and parameters are never parsed as HTML.

Controllers own dynamic labels. State transitions, command syntax, error classification, and approval identities do not use translated display text. Known MCP and skill validation errors are classified before their fixed presentation is translated. Untrusted field names in parser diagnostics stay redacted original text.

Protected actions pass a separate local presentation descriptor to the confirmation UI. The descriptor does not enter worker messages, model messages, tool results, approval fingerprints, or session records. Destinations and bounded arguments remain unchanged and are shown in full as scrollable plain text. Permissions, confirmation frequency, cancellation, stale-context checks, and non-replay rules remain independent of language.

`context-menu.ts` contains only the 18 selection-menu titles needed by the worker. Parity tests compare them with the application catalogs. Storage imports the lightweight tool-ID list, not the executable tool factory, so worker startup does not load the full interface catalogs.

Native metadata lives in source-controlled `_locales/<chrome-locale>/messages.json`. Keep its three messages consistent with the corresponding application catalog. Keep valid manifest `__MSG_...__` references and `default_locale: "en"`; Chrome resolves them at runtime. The build copies these catalogs and audits their shape and references.

## Storage and recovery

The `language` field is part of `piBrowserAgentSettings` in trusted `chrome.storage.local`. It accepts `auto` or one approved application locale. Missing and invalid values read as `en` without an automatic language migration write. No session or IndexedDB schema changes are required.

An older compatible build ignores this additive field and can drop it on a later settings save. Reverting the feature requires reverting manifest references and native catalogs together. Do not clear credentials or sessions to recover language settings. Existing session-tree downgrade limits still apply.

## Checks

Run commands from the repository root:

```sh
npm test -- tests/unit/i18n.test.ts
npm run check
npm test
npm run build
npm run test:e2e
```

E2E checks require a successful production build and use the existing temporary-copy harness with mocked responses. `tests/e2e/i18n.spec.ts` covers preferences, recovery, safe application, all-locale rendering, and focused narrow-layout checks. It does not prove native-language accuracy, screen-reader output, or browser-owned native UI. See the retained review procedure in [manual acceptance](manual-acceptance.md).
